02 走查:从一个真网页写出四段规则

这一页不讲语法,只做一件事:打开一个真网页,把它变成一段跑得通的书源。四条规则一条一条来,每一条都先说「在源代码里看到什么」,再说「所以写成什么」。

先备好一个能试的站

教程自带一个示例书站,地址固定不变,下面每条规则都对着它写:

https://cdn.jsdelivr.net/gh/shizheang/shuhuangyuedu@main/demo/search.html?q=江湖

在浏览器里打开它,然后右键 → 查看网页源代码(不是「检查」—— 我们要看的是原始 HTML,不是被脚本改过之后的 DOM)。后面每一步都用得到这个动作。

示例站一共四页,正好对应书源的四段:

  • search.html —— 搜索结果(一页三本书)
  • book.html?id=1 —— 书籍详情
  • toc.html?id=1 —— 目录
  • c1.html / c2.html / c3.html —— 正文

第 1 步:搜索 —— 先找「每一本」的容器

在搜索页的源代码里往下翻,能看到这么一段:

<div class="result-list">
  <div class="result-item">
    <h3 class="title"><a href="book.html?id=1">江湖夜雨十年灯</a></h3>
    <p class="author">作者：古月</p>
    <p class="intro">一个关于旧友与远行的故事……</p>
  </div>
  <div class="result-item"> …… </div>
  <div class="result-item"> …… </div>
</div>

规律很清楚:外面一个 result-list 是整张列表,里面每个 result-item 是一本书。列表规则要取的就是里面那一层:

"bookList": "class.result-list@class.result-item"

然后在这每一本里再取字段 —— 注意,后面几条都不用再写容器了,因为作用域已经切到单本书里:

"name":    "tag.h3@text"
"bookUrl": "tag.h3@tag.a@href"
"author":  "class.author@text"

name 取到的是「江湖夜雨十年灯」,bookUrl 取到的是 book.html?id=1 —— 相对地址不用管,软件会按来源页补全。

这一步最容易踩的坑

容器和每一项是同一个标签时(上面两者都是 div),很自然会写成 class.result-list@tag.div。它不报错,但结果不对:列表规则会把容器自己也算成一项,于是第一条「书」是整张列表 —— 书名看着还是对的(它取了列表里第一个 h3),而作者变成了「古月、林晚、周叙」三个拼在一起。

判据很好认:第一条数据的字段里出现了本该属于别的条目的内容。改法就是别用标签名,用容器里每一项独有的那个 class(class.result-item)。

第 2 步:详情 —— 从搜索结果点进去

点第一本书,地址变成 book.html?id=1。看它的源代码:

<div class="book-info">
  <img class="book-cover" src="cover.svg">
  <h1 class="book-name">江湖夜雨十年灯</h1>
  <p class="book-author">作者：古月</p>
  <div class="book-intro"> <p>……</p> </div>
  <a class="read-btn" href="toc.html?id=1">查看目录</a>
</div>

这一段写进 ruleBookInfo。它和搜索那一段的区别是:这里没有「每一项」,整页就是一本,所以每条规则直接从头写。

"ruleBookInfo": {
  "name":     "class.book-name@text",
  "author":   "class.book-author@text##作者：##",
  "coverUrl": "class.book-cover@src",
  "intro":    "class.book-intro@html",
  "tocUrl":   "class.read-btn@href"
}

三处值得说:

  • author 后面那串 ##作者：## 是正则替换:把结果里的「作者：」换掉,剩下的才是人名。站点在文字里带了前缀时都得这么剥一次 —— 不剥的话书架上会出现一个叫「作者：古月」的作者。
  • intro 用 @html 而不是 @text:简介里那两段 <p> 要保留,取文字会挤成一坨。
  • tocUrl 是下一段的入口 —— 目录在哪一页由它说了算。找不到它就取不到目录,这是「详情正常、目录为空」最常见的原因。

第 3 步:目录

打开 toc.html?id=1,源代码里:

<ul id="chapter-list">
  <li><a href="c1.html">第一章 雨夜</a></li>
  <li><a href="c2.html">第二章 灯下</a></li>
  <li><a href="c3.html">第三章 十年</a></li>
</ul>

和搜索那段是同一个套路:先取「每一章」的容器(li),再在每一章里取标题与地址。

"ruleToc": {
  "chapterList": "id.chapter-list@tag.li",
  "chapterName": "tag.a@text",
  "chapterUrl":  "tag.a@href"
}

这次不会踩上面那个坑 —— 容器是 ul、每一项是 li,标签名不同,@tag.li 不会把容器自己算进去。

第 4 步:正文

打开 c1.html:

<h2 class="chapter-title">第一章 雨夜</h2>
<div id="content">
  <p>雨是从傍晚开始下的。</p>
  <p>沈砚站在渡口的棚子底下……</p>
</div>
"ruleContent": {
  "content": "id.content@html"
}

同样用 @html 保住段落。正文规则只取正文那一块 —— 连章名一起取进来的话,阅读页每翻一页都会再念一遍章名。

拼起来,就是一份能用的源

{
  "bookSourceUrl": "https://cdn.jsdelivr.net/gh/shizheang/shuhuangyuedu@main/demo/",
  "bookSourceName": "示例书站(教程)",
  "searchUrl": "search.html?q={{key}}",
  "ruleSearch": {
    "bookList": "class.result-list@class.result-item",
    "name": "tag.h3@text",
    "author": "class.author@text##作者：##",
    "bookUrl": "tag.h3@tag.a@href",
    "intro": "class.intro@text"
  },
  "ruleBookInfo": {
    "name": "class.book-name@text",
    "author": "class.book-author@text##作者：##",
    "coverUrl": "class.book-cover@src",
    "intro": "class.book-intro@html",
    "tocUrl": "class.read-btn@href"
  },
  "ruleToc": {
    "chapterList": "id.chapter-list@tag.li",
    "chapterName": "tag.a@text",
    "chapterUrl": "tag.a@href"
  },
  "ruleContent": { "content": "id.content@html" }
}

bookSourceUrl 是整份源的基址:后面所有相对地址(search.html、book.html?id=1、cover.svg)都按它补全。searchUrl 里的 {{key}} 会被替换成你输入的关键词。

这份源在教程仓库的 demo/source.json,可以直接导入试。拿它当模板改:把 bookSourceUrl 换成你要做的站,再照上面四步把每条规则对着那个站的源代码重写一遍。

最后:自己验一遍

导入后在书源调试页逐段跑:搜索 → 详情 → 目录 → 正文。哪一段空,就从那一段往前看一页 —— 因为每一段的入口都是上一段给的地址:

  • 搜索为空 → 先看搜索地址在浏览器里打不打得开,再看列表规则;
  • 详情为空 → 看搜索结果里的书地址对不对;
  • 目录为空 → 多半是 tocUrl 没取到,或列表规则取成了容器;
  • 正文为空 → 看目录里的章节地址对不对,再看正文规则。
